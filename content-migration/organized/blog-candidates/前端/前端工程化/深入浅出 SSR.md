# **一、什么是 SSR（Server-Side Rendering）**

  

**一句话定义：**

  

> SSR 是在服务器端把页面渲染成 HTML，再把完整内容发送给浏览器，让用户能立刻看到首屏，而不是让浏览器下载 JS 再渲染。

  

SSR = 服务端先渲染 → 返回 HTML → 浏览器仍可继续接管成 SPA。

---

# **二、为什么需要 SSR？（面试高频）**

  

前端传统 SPA 的痛点：

1. **首屏白屏时间较长**
    
    浏览器要：
    
    - 下载 JS
        
    - 执行 JS
        
    - 才能看到内容
        
    
    在弱网环境体验差。
    
2. **SEO 差（搜索引擎抓不到内容）**
    
    因为 SPA 初始只有空 HTML + JS。
    
3. **社交分享预览卡片（OG/Twitter 标签）需要内容可抓取**
    

  

SSR 的价值：

- **更快的首屏渲染**（最核心）
    
- **更好的 SEO**
    
- **可生成预渲染内容供爬虫读取**
    

  

总结一句话（可背）：

  

> SSR 解决 SPA 白屏时间长和 SEO 不佳的问题。

---

# **三、SSR 的渲染流程（面试官必问）**

  

### **传统 SPA 流程：**

  

浏览器 → 获取 HTML（基本空） → 下载 JS → JS 渲染 DOM → 才看到页面

  

### **SSR 流程：**

  

服务器 → 调用 JS 框架（React/Vue/Nuxt）在服务器执行 → 生成 HTML → 返回给浏览器 → 浏览器“激活（Hydration）” → 变成正常可交互的 SPA

  

关键步骤：

**HTML 渲染在服务端 → 激活（Hydration）在客户端**

---

# **四、SSR 的关键技术点（面试核心考点）**

  

## **1. 同构（Isomorphic / Universal）**

  

面试常问。

  

解释：

  

> 同样的代码能在服务器和浏览器两边运行。

> 比如 React/Vue 组件，两边都能执行。

  

这样就能：

- 服务器负责首屏渲染
    
- 客户端负责事件绑定、后续交互
    

  

## **2. Hydration（激活）**

  

服务器返回的 HTML 已经有内容，但没有绑定事件。

浏览器下载 JS 后会：

- 对比虚拟 DOM
    
- 给已有的 DOM 绑定事件
    
- 页面进入可交互状态
    

  

**水合（Hydration）是 SSR 的核心难点。**

  

## **3. 路由处理**

  

因为页面在服务器第一次渲染，所以必须让服务器能识别路由路径。

  

例如：

- /user/1
    
- /product/32
    

  

需要：

- 服务器接管路由 → 渲染对应页面
    

  

## **4. 数据预取（Data Fetching）**

  

SSR 时需要提前在服务器获取数据，比如：

- API 请求
    
- 数据库查询
    

  

服务端必须在“渲染前”拿到数据。

---

# **五、SSR 的优势与劣势（面试常问，必背）**

  

## **优点**

- **首屏快**（最快的方式之一）
    
- **SEO 好**（内容直接在 HTML 里）
    
- **可生成完整 Meta 标签**
    

  

## **缺点（面试官爱听，因为说明你理解 trade-off）**

- **服务端压力增大（CPU 消耗）**
    
    因为每个请求都要渲染页面（React/Vue SSR 是 CPU 密集操作）
    
- **部署复杂度提升**（必须跑 Node.js 服务）
    
- **缓存难度大**（HTML 动态生成）
    
- **开发难度更高：要写同构代码**
    
- **不支持某些浏览器只存在的 API（如 window/document）**
    

  

总结：

  

> SSR 是用服务器 CPU 换取更快的用户体验。

# **七、SSR 与 SSG、CSR、ISR 区别（面试超高频）**

  

面试 90% 会点名问：

|**模式**|**描述**|**适用场景**|
|---|---|---|
|**CSR（客户端渲染）**|浏览器下载 JS 自行渲染|SPA，强交互后台|
|**SSR**|每次请求都在服务器渲染|动态页面、SEO、门户|
|**SSG（静态生成）**|构建时生成 HTML|内容固定的文档/博客|
|**ISR（增量静态生成）**|静态 + 定时重新生成|Next.js 特有，适合中大型内容网站|

一句话总结（可以背）：

  

> CSR 交互最强但首屏慢；SSR 首屏最快但服务器压力大；SSG 最便宜但不够动态；ISR 在静态和动态之间做平衡。

# **八、SSR 性能优化（加分项）**

  

如果你能回答这些，面试官会觉得你有经验。

  

### **1. 使用 CDN 缓存 SSR 输出**

  

例如 Next.js：

- 在 CDN 层缓存 HTML
    
- 开启 ISR
    

  

### **2. 静态内容优先 SSG**

  

能静态化就不 SSR

  

### **3. 数据缓存（Redis / HTTP 缓存）**

  

避免重复查询接口

  

### **4. 渲染缓存（render cache）**

  

对 SSR 的 HTML 缓存 10~60 秒

  

### **5. 避免在 SSR 中使用 heavyweight 代码**

  

例如不要在 SSR 里大量计算或导入大模块

# **九、面试高频问题（附简短标准答案）**

  

### **1. SSR 是什么？为什么要用？**

- 服务端渲染 HTML，浏览器直接显示完整页面
    
- 优点：首屏快、SEO 好
    
- 适合电商、资讯、分享页
    

  

### **2. SSR 与 CSR 的区别？**

- CSR 需要 JS 执行后才有内容
    
- SSR 服务端直接给 HTML
    

  

### **3. SSR 中什么是 Hydration？**

- 客户端把服务端返回的 HTML “激活”（绑定事件、恢复交互）
    

  

### **4. SSR 有什么缺点？**

- 服务端压力增加
    
- 部署复杂（需要 Node 服务）
    
- 缓存困难
    
- 开发要求写同构代码
    

  

### **5. Next.js/Nuxt 的运行模式有哪些？**

- SSR
    
- SSG
    
- CSR
    
- ISR
    

  

### **6. SSR 和 SSG 区别？**

- SSR 运行时渲染
    
- SSG 构建时渲染（更快更便宜）
    

  

### **7. SSR 如何做数据预取？**

- 在服务器渲染前请求数据
    
- React：getServerSideProps
    
- Nuxt：asyncData
    

  

### **8. SSR 如何做 SEO？**

- 服务端返回完整的 HTML 内容 + Meta 标签
    
- 爬虫可以直接抓取
    

  

### **9. SSR 怎么优化？**

- CDN 缓存
    
- 渲染缓存
    
- 静态化
    
- 减少首屏 JS
