本质上是：浏览器由于安全设置本身存在同源机制，不允许一个网站随意访问另一个网站的接口，所以会在请求发出之前做同源检查，不同源的请求是不会放行的
最常见的解决方法是，在服务端的响应中配置一些响应头，来允许前端的访问，从而让浏览器放行请求
# **1. 什么是跨域**

**跨域问题是浏览器的安全限制 —— “同源策略”（Same-Origin Policy）导致的。**
**同源要求：协议 + 域名 + 端口完全一致。**

即一个网站不能随便访问另一个网站的接口，除非对方服务器明确允许。

只要三者有一个不一样，就是“跨域”。

|**URL**|**是否同源**|
|---|---|
|https://a.com/api|✓ 同源|
|http://a.com/api|✗ 不同协议|
|https://b.com/api|✗ 不同域名|
|https://a.com:8080/api|✗ 不同端口|

# **2. 为什么存在跨域**

防止 CSRF、盗取用户隐私数据。
例如你登录了银行网站，然后访问某个恶意页面，该页面若能直接调用银行接口，那你的钱就没了。
所以浏览器规定：
> **一个网站不能随便访问另一个网站的接口（跨域），除非对方服务器明确允许。**

注意：

- **跨域限制的是浏览器，不是前端代码本身**
- **Node、curl、Postman 完全不会跨域**

# 最常见的跨域 —— AJAX 请求跨域**

当你前端发送：

```
fetch("https://api.xxx.com/user")
```

而你的前端网页在：

```
https://www.abc.com/
```

协议、域名都不一样，所以跨域。

浏览器会先发一个**预检请求（OPTIONS）**，看看服务器是不是允许你访问。

# **5. CORS（跨域资源共享）是最常见解决方案**

核心即使后端通过配置响应头里的一些字段来允许浏览器放行访问

# **主要响应头与含义**

- Access-Control-Allow-Origin: < origin > | *
    指定允许的来源。**不能与** **Access-Control-Allow-Credentials: true** **一起使用** （浏览器会拒绝）。
- Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
    预检响应中告知允许的方法。
- Access-Control-Allow-Headers: X-Custom-Header, Content-Type
    预检响应中告知允许的自定义请求头。
- Access-Control-Allow-Credentials: true|false
    是否允许携带证书信息（cookies、HTTP auth、客户端 TLS 证书）。若为 true，浏览器会暴露 Set-Cookie，并在后续请求中带上 cookie（如果前端将 credentials 设为 include）。注意：当该值为 true 时，Access-Control-Allow-Origin 必须是明确的 origin，不能是 *。
- Access-Control-Expose-Headers: X-My-Header, Content-Length
    默认浏览器只暴露部分安全响应头（如 Cache-Control、Content-Language、Content-Type 等）。如果你想让前端 response.headers.get('X-My-Header') 能读到，必须暴露它。
- Access-Control-Max-Age: 600
    预检结果缓存秒数。在这段时间内相同的跨域请求不再发 OPTIONS 预检（减少开销）。
- Vary: Origin
    重要：如果后端根据 Origin 动态返回 Access-Control-Allow-Origin，应加 Vary: Origin，以避免代理/CDN 缓存错误的响应造成跨域问题。

## **(1) 简单请求**
如果是简单请求（GET/POST，且头不复杂），浏览器会直接发。
服务端必须返回：

```
Access-Control-Allow-Origin: https://www.abc.com
```

或：

```
Access-Control-Allow-Origin: *
```
## **(2) 复杂请求、预检请求**

当你带了：
- Content-Type: application/json
- 自定义 headers
- PUT/DELETE
浏览器会先发送：

```
OPTIONS /user
```

服务器需返回：

```
Access-Control-Allow-Origin: https://www.abc.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
```

浏览器确认通过后，才会真正发请求。

##  CORS 的常见问题点

### 只设置 Access-Control-Allow-Origin不够

比如你带了 Authorization token

服务器必须额外返回：

```
Access-Control-Allow-Credentials: true
```
并且：
```
Access-Control-Allow-Origin` 不能是 *
```


##  **7. 解决跨域的方式总览（详细讲解）**

## **1. CORS（最主流、最推荐）**

服务端加响应头即可，浏览器自动放行。

**优点：标准、安全、适用所有场景**
**缺点：需要服务器配合**

## **2.反向代理（前端常用）**

使用 nginx / vite devServer / webpack devServer 做一个代理：

```
/api  →  http://backend.com
```

浏览器看到请求是同源的（访问本地代理），就不会跨域。

**优点：前端开发最常用，不改后端**
**缺点：线上部署仍需要 CORS 或网关代理**

## **③ JSONP（历史遗留，不推荐）**

利用< script > 标签不受同源策略的限制的原理 只能用 GET，安全性弱，现在很少用。
## **④ Nginx 中转请求**

Nginx 配置一个 server，把后端 API 转发并处理 CORS。
适合线上。
## **⑤ postMessage（解决 iframe 跨域）**

当你需要跨窗口通信：

```
otherWindow.postMessage("hello", "*");
```

页面之间安全通信，不需要配置服务器。
## **⑥ WebSocket 没有跨域**

因为 WebSocket 不受同源策略限制。
但如果是浏览器环境 + HTTP upgrade，服务端仍需处理权限。
## **常见题目**

## **为什么 localhost:3000 调 127.0.0.1:3000 也算跨域？**
  
因为**域名不同**，同源策略严格匹配包括
- 协议
- 域名（字符串）
- 端口

虽然都指向本机，但浏览器不管。
## **跨域是前端的问题还是后端的问题？**

准确说：
- 跨域是浏览器的限制（属于前端环境的问题）
- 但**必须后端同意**你访问才能放行

所以通常是后端加 CORS。
## **为什么用 Postman 不会跨域？**

因为跨域限制只属于浏览器的安全策略。
Postman/Node 不执行同源策略。
## **Access-Control-Allow-Origin: * 和带 cookie 可以一起用吗？**

不能。
带 cookie 时必须：

```
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: 具体域名
```
