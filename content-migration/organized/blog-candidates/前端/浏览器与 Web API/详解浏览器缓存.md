# **一、什么是浏览器缓存**

浏览器为了 **减少网络请求、提升加载速度、降低服务器压力**，会把资源（HTML/CSS/JS/图片等）存储在本地或中间代理中，下次访问时优先使用缓存。
浏览器缓存实际上是一种策略的选择，即开发者通过响应头/一些配置来决定给不同的文件应用不同的缓存策略，从而达到提升性能和体验的目的
# **二、浏览器缓存策略的分类**

浏览器缓存策略可分为两大类：
## **1. 强缓存（Strong Cache / Local Cache）**

特点：
- **不会向服务器发送请求**
- 直接使用本地缓存
- 命中强缓存，状态码：**200 (from disk/memory cache)**
判断依据（响应头）：主要是通过 cache-control 这个响应头的内容来判断缓存策略以及具体的方式

| **Header**                     | **说明**                                             |
| ------------------------------ | -------------------------------------------------- |
| **Cache-Control: max-age=xxx** | HTTP/1.1 推荐方式，指定缓存时间，即有 max-age 这个属性就代表在这个时间内启用强缓存 |
| **Expires**                    | HTTP/1.0，绝对时间，可能受本地时间影响                            |
### Cache-Control 常见指令：
Cache-Control 是 HTTP/1.1 的缓存控制主指令，用来告诉浏览器和中间缓存（CDN / 代理）**是否缓存、缓存多久、以及如何验证**。它比旧式 Expires 更灵活、现代，是首选。

#### **1) 有效期相关（强缓存）**

- max-age=< seconds >
    资源在本地/代理缓存的**最大存活时间**（秒）。命中期间不会向服务器发请求（强缓存）。
    示例：Cache-Control: max-age=31536000（一年）
- s-maxage=< seconds >
    与 max-age 类似，但**只对共享缓存（CDN / 代理）生效**，比 max-age 优先。
    场景：浏览器短缓存但 CDN 长缓存，或反之。
- immutable
    告诉“支持”的浏览器在 max-age 有效期内，即使用户手动刷新（正常刷新）也不再去验证资源（提高性能）。通常用于带 hash 的静态文件。 
#### **2) 验证 / 协商缓存相关**

- no-cache
    **允许缓存，但每次使用前必须向服务器验证**（If-None-Match / If-Modified-Since）。别只记“不能缓存”——这是坑点之一。
- must-revalidate
    过期后**必须**与源站验证，不能使用陈旧内容（即便网络断开也不允许使用过期缓存，除非另有 stale-while-revalidate 等）。
#### **3) 禁止缓存**

- no-store
    **不允许任何地方存储响应**（既不存磁盘也不存内存）。用于高敏感数据（银行页面、个人身份信息等）。与 no-cache 很容易混淆 — 要强调 no-store 是彻底不缓存。
#### **4) 共享 / 私有**

- public
    允许任何中间缓存（如 CDN）缓存，即使响应含有 Set-Cookie 也可被缓存（不过一般不和 Set-Cookie 同用）。默认多数静态资源可标 public。
- private
    只允许浏览器缓存，不允许代理/共享缓存缓存（用于用户个性化内容）。
### **5) 过期策略（现代扩展）**

- stale-while-revalidate=< seconds >（非标准但被广泛支持）
    在内容过期后仍可立即使用陈旧缓存，同时后台异步向服务器拉取更新并替换缓存 — 用户获得低延迟和最终一致性。
- stale-if-error=< seconds >
    当回源出现错误（5xx/超时）时，允许使用过期缓存作为兜底。

优先级：
```
Cache-Control > Expires
```
即有 cache-control 的时候的以 cache-control 为准
## **2. 协商缓存（Negotiated Cache / Validation Cache）**

特点：
- **会向服务器发送请求**
- 判断资源是否变更
- 未变更返回 **304 Not Modified**，继续使用本地缓存
判断依据（响应头 + 请求头配对）：
### **方案 A：基于时间**

|**响应头**|**请求头**|
|---|---|
|**Last-Modified**|**If-Modified-Since**|

不足：
- 时间粒度秒级
- 内容变了但时间没变 → 误判
- 时间变了但内容没变 → 仍然 304，导致性能浪费
### **方案 B：基于内容哈希**

|**响应头**|**请求头**|
|---|---|
|**ETag**|**If-None-Match**|

优势：
精确判断内容变化
适用于频繁变动的资源
现代 Web 采用最多
优先级：

```
ETag > Last-Modified
```

# **三、浏览器缓存的读取优先级**

整体流程如下：

```
1. 查强缓存是否有效
   ├─ 有效 → 直接使用（200 from cache）
   └─ 无效 → 进入协商缓存

2. 协商缓存判断资源变动
   ├─ 未变化 → 304，继续使用缓存
   └─ 已变化 → 下载新资源（200）
```

面试可能会追问：

> 刷新行为对缓存的影响？
### **普通刷新（F5）**

- **跳过强缓存**
- **仍可走协商缓存**
### **强制刷新（Ctrl + F5）**

- **跳过强缓存**
- **跳过协商缓存**
- 资源直接重新下载
# **五、缓存控制策略怎么配置？**

### **静态资源采用：**

```
Cache-Control: max-age=31536000, immutable
```

原因：
- 版本号/哈希变化 → 浏览器自动拉新文件
- 文件名没变 → 永远有效（immutable）
### **HTML 通常设置：**

```
Cache-Control: no-cache
```

或：

```
Cache-Control: no-store
```

区别：

| **指令**       | **是否存本地** | **是否会与服务器验证** |
| ------------ | --------- | ------------- |
| **no-cache** | 可存        | 每次重新验证        |
| **no-store** | 不存        | 每次重新请求        |
面试高频点：

> SPA 首页 HTML 必须确保获取最新版本，否则 JS/CSS 不更新。
# **六、Service Worker 缓存（PWA）**

特点：
可离线
可自定义缓存策略
适合 WebApp

常用策略示例：

|**策略**|**含义**|
|---|---|
|Cache First|速度最快|
|Network First|确保最新|
|Stale While Revalidate|最佳性能和一致性|
# **七、常见问题与标准回答**

### **强缓存和协商缓存的区别**

→ 不只说“是否发请求”，要加上“判断依据 + 响应码”
### **ETag 和 Last-Modified 关系**

→ 说优先级 + 说精确原因
### **哈希文件是否需要协商缓存**

标准答案：

```
带哈希的静态资源，不应该走协商缓存，
应直接使用强缓存。
```
### **HTML 为什么不能强缓存**

标准答案：

```
因为 HTML 是入口文件，
如果被强缓存，资源版本更新无法感知。
```
### **刷新方式与缓存的关系**

提 F5 / Ctrl+F5 区别即可
