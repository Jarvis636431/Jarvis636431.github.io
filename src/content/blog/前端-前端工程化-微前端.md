## 一、什么是微前端（Micro Frontends）
> 微前端就是把一个大型前端应用拆成多个独立可部署的小应用（Micro Apps），它们可以被主应用（基座）动态加载、独立开发部署、技术栈可不同。

和微服务对应，但对象是浏览器端。

---

## 二、为什么需要微前端（核心痛点）

面试常问“为什么要用？”

**1. 单体前端巨大（Monolith）导致：**

- 发布一次需要打包整个项目 → 耗时且风险高
- 多团队共同开发冲突多
- 公共部分更新会影响整体
  
**2. 公司内部多个业务线：**
- 各个业务团队技术栈不一致（Vue、React、Angular）
- 希望能在同一个页面“拼装”它们
**3. 独立开发、独立部署的诉求强烈：**
- 升级某个业务不影响其他业务
- 各模块可以灰度上线
## 三、微前端的核心理念（面试必背）

**1. 技术栈无关（最重要）**
各子应用可以随便用 Vue/React/Angular 不互相干扰。
**2. 独立部署**
每个应用自己构建、自己部署 → 主应用只负责加载。
**3. 运行时动态加载**
可在运行期切换不同子应用，比如路由切换时加载对应 App。
**4. 松耦合**
子应用之间尽量不要直接通信，应该通过全局通信机制（EventBus/Shared Store）。
## 四、常见微前端解决方案（面试高频）

### **1. Qiankun（蚂蚁开源，基于 single-spa）**
优点：
- 国内社区最大
- 接入简单
- 支持沙箱隔离（CSS/JS）
缺点：
- 依赖 single-spa
- 对沙箱隔离还是不够彻底
- 应用多时性能有损耗
### **2. Single-spa**
优点：
- 机制简单
缺点：
- 功能不够完善
- 没有资源沙箱、CSS 隔离等
### **3. Module Federation（Webpack 5）**

优点：
- 真正的“运行时模块共享”
- 打破构建时依赖（跨项目共享组件）
- 构建产物可按需加载
缺点：
- 对打包结构依赖强
- 更适合同一技术栈项目之间共享（例如 React 多项目）

### **4. EMP（WebPack + Module Federation 国内方案）**
### **5. Web Components 方案（原生）**
优点：

- 天生隔离 ShadowDOM
缺点：
- 生态差，实践少

  

**面试备注：**

  

> 大厂普遍使用 Qiankun + 自研方案 + Module Federation

## 五、微前端关键技术点（面试核心）

  

## **1. 应用隔离**
常见面试点。
### **（1）JS 运行隔离 —— 沙箱（sandbox）**
- snapshotSandbox（快照）
- proxySandbox（通过 Proxy 代理 window，对化）
Qiankun 的实现：
- LegacySandbox
- ProxySandbox
### **（2）CSS 样式隔离**
常见方法：
- Shadow DOM
- CSS prefix（样式前缀）
- 动态作用域隔离（例如 qiankun 的 scoped css）
面试答法：

> 微前端必须解决样式冲突问题，常用 ShadowDOM 彻底隔离，或通过 css-scope、CSS-in-JS、动态前缀解决。
## **2. 静态资源隔离**

子应用的 JS/CSS 在加载时要有作用域，不能污染主应用。
Qiankun：把 script 标签变成 eval + 沙箱隔离。
## **3. 通信机制（非常常见）**
子应用之间如何通信？

  

常见方式：

1. **全局事件总线（EventBus）**
2. **基座下发 props**
3. **Shared Store（例如 RxJS、Redux）**
4. **发布订阅（Pub/Sub）**
  

背法：

  

> 微前端追求松耦合，通信应尽量采用事件机制，而不是相互 import。

---

## **4. 路由管理（必问）**

  

方案：

1. 主应用路由分发，在某个路由下挂载子应用
    
2. 子应用自己维护内部路由
    

  

常见面试点：

  

> Hash 路由最容易实现，因为不会和主应用 history 冲突；History 路由需要配置服务器重定向，否则刷新会 404。

---

## **5. 性能问题（面试常问）**

  

面试官常问：“微前端会不会影响首屏性能？”

  

答法：

- 会的，因为需要加载多个 bundle
    
- 通常会延迟加载子应用，首屏只加载主应用
    
- 通过预加载、资源复用、共享依赖（Module Federation）优化性能
    

---

## 六、真实企业实践注意点（面试亮点）

  

### **1. 公共依赖（React、Vue）是否多份？**

  

要共享依赖，否则 React 可能被加载多份 → 冲突、性能差。

Webpack Module Federation 可以解决依赖重复问题。

  

### **2. 子应用打包要求统一**

- 打成 umd 格式
    
- 公共资源路径要相对路径
    
- 打包产物不能 hash
    

  

### **3. 子应用降级策略**

  

如果某个子应用挂了？

- 提供 fallback
    
- 或主应用做加载失败兜底

## 七、微前端 VS 单页应用 VS 多页应用（面试可能问）

|**特性**|**微前端**|**SPA**|**MPA**|
|---|---|---|---|
|部署|多独立部署|单体部署|多页面部署|
|技术栈|可不同|同一|同一|
|切换体验|类似 SPA|单页|切页刷新|
|隔离复杂度|高|无|无|
|性能|适中需优化|好|视情况|

---

## 八、微前端的优缺点（面试经典题）

  

## **优点**

- 技术栈自由
    
- 团队自治、独立开发部署
    
- 大型项目解耦
    
- 可渐进式升级老项目
    

  

## **缺点**

- 性能损耗（多应用加载）
    
- 开发复杂度提高（沙箱、通信、路由）
    
- 构建运维成本变高
    
- 不适合小项目
    

  

面试建议回答：

  

> 微前端是“收益大但工程复杂”的方案，只适用于多团队、多业务线的大型系统。

## 九、面试高频题（附标准答案）

  

### **1. 为什么要用微前端？**

- 解决大型系统前端难以维护
    
- 多团队并行独立开发
    
- 独立部署降低风险
    
- 技术栈不统一的问题
    

  

### **2. 微前端的核心解决方案是什么？**

- JS 沙箱（JS 隔离）
    
- CSS 隔离
    
- 路由分发
    
- 子应用独立打包部署
    

  

### **3. 常用的微前端框架？优劣？**

- Qiankun（最成熟）
    
- Single-spa（核心机制）
    
- Module Federation（共享依赖）
    
- Web Components（原生但生态弱）
    

  

### **4. 微前端如何解决样式冲突？**

- Shadow DOM
    
- CSS 前缀
    
- 动态 scope
    
- CSS-in-JS
    

  

### **5. 微前端如何通信？**

- EventBus
    
- 全局状态
    
- props 传递
    

  

### **6. 微前端会带来什么性能问题？如何优化？**

  

问题：

- 额外请求
    
- 多份依赖
    

  

优化：

- 共享依赖（MF）
    
- 延迟加载
    
- 预加载
    
- 缓存策略
    

  

### **7. 微前端的 JS 沙箱怎么实现？（硬核）**

  

背这个最有用：

  

> 沙箱通过 Proxy 代理 window，对每个子应用创建独立的全局对象，拦截读写操作，从而隔离全局变量。

  

### **8. 什么时候不适合使用微前端？**

- 项目不大
    
- 团队人数不多
    
- 技术栈统一
    
- 构建部署流程简单
    

  

面试官听到这个会觉得你理解“trade-off”。
