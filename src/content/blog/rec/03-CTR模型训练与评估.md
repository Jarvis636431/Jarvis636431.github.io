一个 CTR 模型不只是“把代码跑起来”。完整实验需要回答三类问题：

```text
模型是否学得动？
模型是否能正确排序？
模型输出的概率是否可信？
```

它们分别对应训练损失、AUC、LogLoss 和概率校准等观察维度。这篇文章把数据划分、训练循环和评估指标串成一条完整链路。

## 1. CTR 模型的训练目标

CTR 模型预测的是：

```text
pCTR = P(点击=1 | 用户、候选、上下文、曝光)
```

一条有效曝光样本的标签是：

```text
曝光后点击   → y = 1
曝光后未点击 → y = 0
```

模型通常不会直接输出“点击”或“不点击”，而是输出一个点击概率。这个概率既可以参与候选排序，也可能参与广告价值计算。

以 LR 为例：

```text
z = wᵀx + b
p = sigmoid(z)
```

其中 `z` 是 logit，`p` 是预测点击概率。

## 2. 训练集、验证集和测试集

实验数据通常分为三个部分：

| 数据集 | 用途 | 是否更新参数 |
| --- | --- | --- |
| 训练集 | 学习模型权重 | 是 |
| 验证集 | 选择超参数、训练轮数和模型版本 | 否 |
| 测试集 | 最终评估泛化能力 | 否 |

搜广推数据具有明显的时间属性，因此通常优先采用时间切分：

```text
较早数据 → 训练集
中间数据 → 验证集
较晚数据 → 测试集
```

这比随机切分更接近真实线上场景：使用过去的数据训练，再预测未来的用户行为。

### 2.1 防止数据泄漏

标准化所需的均值和标准差只能从训练集计算：

```text
训练集 → 计算 mean 和 std
训练集、验证集、测试集 → 使用同一组 mean 和 std
```

如果先用全部数据计算统计量，验证集和测试集的信息就提前进入了训练流程。这是一种数据泄漏，会使离线结果过于乐观。

## 3. 一次 Mini-batch 训练发生了什么

一次基本训练迭代包含以下步骤：

```text
取出一批特征和标签
  ↓
前向传播得到 logits
  ↓
计算 BCE 损失
  ↓
反向传播计算梯度
  ↓
优化器更新参数
```

对应的 PyTorch 代码是：

```python
for features, labels in train_loader:
    optimizer.zero_grad()

    logits = model(features)
    loss = criterion(logits, labels)

    loss.backward()
    optimizer.step()
```

每一行的作用如下：

| 代码 | 作用 |
| --- | --- |
| `optimizer.zero_grad()` | 清空上一个 Batch 累积的梯度 |
| `model(features)` | 前向传播，得到 logits |
| `criterion(logits, labels)` | 计算当前 Batch 的损失 |
| `loss.backward()` | 反向传播，计算参数梯度 |
| `optimizer.step()` | 根据梯度更新模型参数 |

一次完整遍历全部训练数据称为一个 Epoch。一个 Epoch 中通常包含多个 Mini-batch，因此参数也会更新多次。

## 4. 为什么训练时使用 BCEWithLogitsLoss

理论上，LR 的输出流程是：

```text
logits → Sigmoid → 概率 → 二元交叉熵
```

二元交叉熵为：

```text
BCE(y,p) = -[y log(p) + (1-y)log(1-p)]
```

但训练代码通常写成：

```python
criterion = torch.nn.BCEWithLogitsLoss()
loss = criterion(logits, labels)
```

`BCEWithLogitsLoss` 在内部以数值稳定的方式组合 Sigmoid 和 BCE。它直接接收 logits，而不是已经经过 Sigmoid 的概率。

```python
# 正确
loss = criterion(logits, labels)

# 错误：重复执行了 Sigmoid
loss = criterion(torch.sigmoid(logits), labels)
```

评估时才显式计算概率：

```python
probabilities = torch.sigmoid(logits)
```

## 5. 为什么不能只看准确率

CTR 数据通常高度不平衡。假设有一万次曝光：

```text
点击：100
未点击：9900
```

如果模型对所有样本都预测“不点击”：

```text
Accuracy = 9900 / 10000 = 99%
```

准确率高达 99%，但这个模型不能找出任何更可能点击的候选，也没有实际排序价值。

因此 CTR 评估更常关注：

- AUC：正负样本的相对排序能力；
- LogLoss：预测概率与真实结果的吻合程度；
- Calibration：预测概率与实际发生频率是否一致。

## 6. AUC：模型能否把正样本排在负样本前面

AUC 可以直观理解为：

> 随机抽取一个正样本和一个负样本，模型让正样本得分高于负样本的概率。

例如：

```text
正样本：真实点击，预测 0.08
负样本：真实未点击，预测 0.03
```

正样本分数更高，这一对的顺序正确。

如果：

```text
正样本：预测 0.02
负样本：预测 0.07
```

这一对的顺序错误。

### 6.1 AUC 的基本解释

| AUC | 一般含义 |
| ---: | --- |
| 0.5 | 接近随机排序 |
| 小于 0.5 | 排序方向可能相反 |
| 越接近 1 | 正负样本区分能力越强 |
| 1.0 | 所有正样本都排在所有负样本之前 |

不能脱离数据集和业务场景规定一个统一的“优秀 AUC”。不同标签噪声、样本构造和数据切分方式下的结果不能直接横向比较。

### 6.2 AUC 只关心顺序

考虑两个模型：

```text
模型 A：正样本 0.90，负样本 0.40
模型 B：正样本 0.09，负样本 0.04
```

两者都把正样本排在负样本前面，因此在这一对样本上的排序表现相同。AUC 不会因为模型 A 的数值更大就认为它更好。

所以 AUC 回答的是：

> 谁应该排在前面？

而不是：

> 预测的概率数值是否准确？

## 7. LogLoss：模型给出的概率是否合理

在二分类 CTR 场景中，LogLoss 通常就是二元交叉熵：

```text
LogLoss(y,p) = -[y log(p) + (1-y)log(1-p)]
```

对于 `N` 条样本，取平均：

```text
LogLoss
= -1/N × Σ[yᵢlog(pᵢ) + (1-yᵢ)log(1-pᵢ)]
```

其中：

- `yᵢ` 是真实的 `0/1` 标签；
- `pᵢ` 是模型预测点击的概率；
- LogLoss 越小越好。

### 7.1 正样本

当 `y=1` 时：

```text
LogLoss = -log(p)
```

```text
p=0.99 → 损失很小
p=0.10 → 损失较大
p=0.01 → 损失非常大
```

### 7.2 负样本

当 `y=0` 时：

```text
LogLoss = -log(1-p)
```

```text
p=0.01 → 损失很小
p=0.90 → 损失较大
p=0.99 → 损失非常大
```

LogLoss 会强烈惩罚“非常自信但预测错误”的结果。

## 8. LogLoss 和 BCE 是不是同一个公式

在当前二分类任务中，它们通常是同一个数学量，只是名称强调的角度不同：

- BCE 强调它作为模型训练损失函数的角色；
- LogLoss 强调它作为概率预测评估指标的角色。

训练时：

```python
loss = torch.nn.BCEWithLogitsLoss()(logits, labels)
```

评估时：

```python
probabilities = torch.sigmoid(logits)
metric = sklearn.metrics.log_loss(labels, probabilities)
```

如果样本、平均方式和权重完全相同，两者的数值应该基本一致。微小差异可能来自概率裁剪、数值精度或接口实现。

## 9. AUC 与 LogLoss 的区别

| 问题 | AUC | LogLoss |
| --- | --- | --- |
| 主要衡量 | 相对排序能力 | 概率预测质量 |
| 趋势 | 越大越好 | 越小越好 |
| 是否关心概率绝对值 | 基本不关心 | 非常关心 |
| 是否强烈惩罚自信但错误 | 否 | 是 |
| 典型用途 | 候选排序 | 概率预估、训练目标和价值计算 |

最容易记忆的区别是：

```text
AUC：谁应该排在前面？
LogLoss：你说的概率可信吗？
```

### 9.1 AUC 好但 LogLoss 差

模型可能保持了正确顺序，但把所有概率预测得过高：

```text
正样本：0.90
负样本：0.80
```

排序正确，但如果真实 CTR 很低，概率严重高估，LogLoss 会较差。

### 9.2 LogLoss 尚可但 AUC 很差

如果整体 CTR 是 3%，模型对所有样本都预测：

```text
pCTR = 0.03
```

它至少接近总体平均概率，LogLoss 未必极差，但所有样本分数相同，AUC 约为 0.5，没有个性化排序能力。

## 10. 概率校准：预测概率是否等于实际发生频率

校准关心的是：

```text
预测概率 ≈ 实际发生频率
```

例如取出一千条预测概率约为 10% 的曝光：

```text
如果约有 100 次点击 → 校准较好
如果只有 20 次点击  → 模型高估
如果有 300 次点击    → 模型低估
```

校准对广告系统非常重要。假设系统使用：

```text
预期点击价值 = pCTR × 单次点击价值
```

即使候选排序正确，只要 `pCTR` 整体偏高或偏低，也会影响广告价值计算、预算分配和计费。

### 10.1 ECE

Expected Calibration Error 会把预测概率分桶，比较每个区间中的平均预测概率和实际点击率，再按样本数量加权：

```text
ECE 越接近 0，整体校准误差越小
```

ECE 是校准的简化摘要，仍需结合校准曲线和分桶明细观察，不能只依赖一个数字。

## 11. 训练指标和评估指标的关系

训练时，优化器直接最小化 BCE：

```text
参数更新方向 ← BCE 的梯度
```

AUC 通常不直接作为基础 LR 的训练损失，因为它基于样本之间的相对顺序，难以像 BCE 一样对单个样本直接、稳定地求梯度。

因此常见流程是：

```text
用 BCE / LogLoss 训练
用 LogLoss 检查概率质量
用 AUC 检查排序能力
用校准指标检查概率与实际频率
```

损失函数决定模型怎样学习，评估指标决定我们从哪些角度判断模型是否有用。两者可以相同，也可以不同。

## 12. 如何观察训练过程

每个 Epoch 至少记录：

```text
Train Loss
Validation Loss
```

常见现象如下。

### 12.1 正常学习

```text
Train Loss 下降
Validation Loss 下降并逐渐稳定
```

说明模型正在学到能够泛化的规律。

### 12.2 过拟合

```text
Train Loss 持续下降
Validation Loss 先下降后上升
```

说明模型越来越适应训练数据，但在未见数据上表现变差。

### 12.3 没有学动

```text
Train Loss 基本不变
Validation Loss 基本不变
AUC 接近 0.5
```

可能原因包括：

- 学习率太小；
- 特征中没有预测信息；
- 标签或特征关联错误；
- 参数没有真正更新；
- 数据处理存在问题。

### 12.4 训练不稳定

```text
Loss 大幅震荡或出现 NaN
```

可能原因包括学习率过大、输入数值范围异常、数值溢出或数据中存在非法值。

## 13. LR 实验怎样验证这些概念

对应实验位于：

```text
rec-lab/models/lr
```

运行基础版本：

```bash
uv run python -m models.lr.train
```

加入人工交叉特征：

```bash
uv run python -m models.lr.train --include-cross
```

实验输出：

```text
auc
log_loss
ece
predicted_ctr
observed_ctr
bce_from_torch
```

其中 `bce_from_torch` 和 `log_loss` 使用不同接口计算同一个数学量。它们应当基本一致，可以帮助验证“二分类 LogLoss 就是 BCE”。

两组实验需要比较：

以下结果使用 20,000 条样本、40 个 Epoch、Batch Size 256、学习率 0.05 和随机种子 42：

| 观察项 | Baseline | 加入交叉特征 | 变化 |
| --- | ---: | ---: | ---: |
| AUC | 0.738938 | 0.757314 | +0.018376 |
| LogLoss | 0.292002 | 0.285596 | -0.006406 |
| ECE | 0.014450 | 0.008108 | -0.006342 |
| 预测 CTR | 10.5475% | 10.5094% | 更接近实际 CTR |
| 实际 CTR | 10.3667% | 10.3667% | 不变 |

两组实验只改变是否提供 `sports_match = user_sports × item_sports`。加入它以后，AUC 上升，LogLoss 下降约 2.19%，ECE 下降约 43.9%。这说明模型不仅获得了更好的排序能力，输出概率的质量和校准表现也同时改善。

### 13.1 训练过程是否正常

Baseline 的 Validation Loss 从 0.455192 降至 0.287810；加入交叉特征后，从 0.420732 降至 0.281647。两组实验的 Train Loss 和 Validation Loss 都同步下降，在 25～30 个 Epoch 后逐渐稳定，没有出现明显的过拟合迹象。

### 13.2 权重变化说明了什么

| 特征 | Baseline 权重 | 加入交叉特征后的权重 |
| --- | ---: | ---: |
| `user_sports` | +0.576785 | +0.202694 |
| `item_sports` | +0.541536 | +0.118882 |
| `price` | -0.440745 | -0.450973 |
| `position` | -0.290694 | -0.305797 |
| `is_evening` | +0.162284 | +0.165271 |
| `sports_match` | — | +0.518141 |

Baseline 看不到“用户喜欢运动且商品属于运动类别”这一乘法关系，只能把匹配带来的部分点击提升分摊给 `user_sports` 和 `item_sports`。显式加入 `sports_match` 后，两个一阶特征的权重下降，而匹配特征获得较大的正权重。模型由此能够分别表达用户偏好、商品类别和二者匹配带来的额外影响。

这里展示的是标准化特征空间中的权重，适合比较方向及两次实验间的变化，但不能直接与数据生成器中的原始系数逐项比较。

### 13.3 这次对照实验的结论

LR 能为输入中已有的特征学习线性权重，却不会自动创造乘法交叉特征。人工提供 `user_sports × item_sports` 后，排序、概率质量和校准均得到改善。这正是传统 LR CTR 模型依赖特征工程的原因之一，也为后续学习能够自动建模二阶交互的 FM 提供了实验动机。

## 14. 一次完整实验的检查清单

### 数据

- 标签是否只由有效曝光产生？
- 训练、验证和测试是否按正确口径切分？
- 标准化统计量是否只来自训练集？
- 是否存在未来信息或标签泄漏？

### 训练

- 模型返回的是 logits 还是概率？
- `BCEWithLogitsLoss` 前是否错误地重复执行 Sigmoid？
- 每个 Batch 前是否清空梯度？
- 参数是否真正更新？
- Train Loss 和 Validation Loss 是否符合预期？

### 评估

- AUC 是否明显优于随机排序？
- LogLoss 是否优于简单基线？
- 预测 CTR 是否接近实际 CTR？
- 校准误差是否合理？
- 结果在不同随机种子下是否稳定？

### 解释

- 模型权重方向是否符合业务和数据生成规律？
- 指标变化来自模型改进还是数据口径变化？
- 新增特征带来的提升是否稳定？
- 离线提升是否值得额外的线上计算成本？

## 15. 总结

1. CTR 训练使用历史曝光的 `0/1` 标签学习点击概率。
2. 训练集更新参数，验证集选择方案，测试集负责最终评估。
3. 数据预处理统计量只能从训练集计算，避免数据泄漏。
4. `BCEWithLogitsLoss` 接收 logits，内部完成数值稳定的 Sigmoid 与 BCE。
5. 在二分类场景中，LogLoss 与 BCE 通常是同一个数学公式。
6. AUC 衡量相对排序，LogLoss 衡量概率质量，校准衡量概率与实际频率的一致性。
7. 准确率在低 CTR、类别不平衡场景中可能具有强烈误导性。
8. AUC 好不代表概率准确，LogLoss 尚可也不代表模型具有排序能力。
9. 模型实验需要同时观察训练过程、排序能力、概率质量和校准情况。
10. 指标只是证据，最终还要结合数据口径、业务目标、稳定性和线上成本解释。
